**Дисципліна:** Моделювання систем  

---

## 1. Мета роботи
Ознайомлення з принципами об’єктно-орієнтованого підходу до побудови імітаційних моделей дискретно-подійних систем (ДПС). Опанування механізму просування модельного часу за принципом найближчої події (*Next-Event Time Advance*). Програмна реалізація, розширення та верифікація імітаційної моделі системи масового обслуговування мовою C# з підтримкою багатоканальності та складної топології маршрутизації (включаючи розгалуження та зворотні зв'язки).

## 2. Завдання до роботи
1. Реалізувати алгоритм імітації простої моделі обслуговування одним пристроєм з використанням об’єктно-орієнтованого підходу (мова C#).
2. Модифікувати алгоритм, додавши обчислення середнього завантаження пристрою.
3. Створити модель послідовної СМО за схемою: `CREATE -> PROCESS 1 -> PROCESS 2 -> PROCESS 3 -> DISPOSE`.
4. Виконати верифікацію моделі за завданням 3, змінюючи значення вхідних змінних та параметрів моделі. Навести результати верифікації у таблиці.
5. Модифікувати клас `PROCESS`, щоб можна було його використовувати для моделювання процесу обслуговування кількома ідентичними пристроями (багатоканальний пристрій).
6. Модифікувати клас `PROCESS`, щоб можна було організовувати вихід у два і більше наступних блоків, зокрема з поверненням у попередні блоки (розгалуження та зворотний зв’язок).

## 3. Об’єктно-орієнтована архітектура моделі
Програма побудована за модульним принципом, де кожен клас винесено в окремий файл:

* **`Element` (`Element.cs`)** — базовий абстрактний клас елемента моделі. Містить атрибути часу (`tcurr`, `tnext`), стану (`state`), закону розподілу (`distribution`, `delayMean`, `delayDev`), кількості оброблених вимог (`quantity`) та віртуальні методи життєвого циклу: `InAct()`, `OutAct()`, `DoStatistics(delta)`.
* **`Create` (`Create.cs`)** — елемент-джерело, що генерує надходження вимог за випадковим законом (експоненційним) та ініціює їх вхід до наступного елемента через `InAct()`.
* **`Process` (`Process.cs`)** — обслуговуючий пристрій. Реалізує чергу обмеженої місткості (`maxqueue`), багатоканальне обслуговування ($N$ приладів), статистику завантаження та маршрутизацію вихідних потоків за ймовірностями.
* **`Dispose` (`Dispose.cs`)** — стік системи (Sink), що підраховує кількість вимог, які повністю завершили обслуговування та покинули систему.
* **`Route` (`Route.cs`)** — дескриптор напрямку переходу. Містить посилання на цільовий елемент (`NextElement`), апріорну ймовірність (`Probability`) та лічильник фактичних переходів (`TransitionCount`).
* **`Model` (`Model.cs`)** — керуючий диспетчер моделювання. Реалізує глобальний цикл просування модельного часу за принципом найближчої події, синхронізацію часу між елементами та збір інтегральних статистик.
* **`FunRand` (`FunRand.cs`)** — генератор випадкових величин (експоненційний, рівномірний та нормальний за перетворенням Бокса-Мюллера).

## 4. Принцип просування модельного часу
У даній роботі застосовано **принцип найближчої події (*Next-Event Time Advance*)**. Модельний час не інкрементується дрібними фіксованими кроками $\Delta t$, а **миттєво телепортується** до моменту настання найближчої запланованої події:
$$t_{curr} = \min_{e \in Elements} \{ t_{next}^{(e)} \}$$

Між подіями стан системи не змінюється, тому всі проміжні «порожні» інтервали пропускаються. Це забезпечує максимальну швидкодію обчислень та абсолютну точність без похибок дискретизації часу.

```csharp
// Фрагмент циклу Model.Simulate:
tnext = Double.MaxValue;
foreach (Element e in list) {
    if (e.GetTnext() < tnext) {
        tnext = e.GetTnext(); // Знаходження найближчої події
        eventId = e.GetId();
    }
}
// Інтегрування характеристик за інтервал (tnext - tcurr):
foreach (Element e in list) e.DoStatistics(tnext - tcurr);

tcurr = tnext; // Миттєвий стрибок часу
list[eventIndex].OutAct(); // Виконання події
```

## 8. Результати виконання завдання 5 (Багатоканальний пристрій)
Клас `Process` розширено підтримкою довільної кількості паралельних ідентичних приладів:
* Кожен канал має власний стан `channelStates[i]` та таймер звільнення `tnextChannels[i]`.
* Заявка займає будь-який вільний пристрій; до черги заявка потрапляє тільки у випадку, коли зайняті **всі** канали.

### Теоретична верифікація за формулами СМО $M/M/c$:
Вхідна інтенсивність $\lambda = 1.0$ (mean = 1.0), обслуговування одним каналом $\mu = 0.5$ (mean = 2.0), кількість каналів $c = 3$.
$$\rho_{теор} = \frac{\lambda}{c \cdot \mu} = \frac{1.0}{3 \cdot 0.5} = \frac{2}{3} \approx 0.6667 \ (66.67\%)$$

| Показник | Теоретичне значення | Емпіричне значення |
| :--- | :---: | :---: |
| Кількість каналів ($c$) | 3 | 3 |
| **Коефіцієнт завантаження каналу ($\rho$)** | **0.6667 (66.7%)** | **0.6838 (68.4%)** |
| Середня кількість зайнятих каналів | 2.0000 | 2.0513 з 3 |
| **Баланс вимог в системі** | **1060** | **1028 (обслуговано) + 27 (відмови) + 5 (в системі) = 1060** |

*Висновок:* Баланс вимог виконується зі 100% точністю, а коефіцієнт завантаження збігається з теоретичним значенням з похибкою менше $1.8\%$.

## 9. Результати виконання завдання 6 (Розгалуження та зворотний зв'язок)
Реалізовано систему маршрутизації за кумулятивними ймовірностями `Route(NextElement, Probability)`.

### Схема експериментальної моделі:
* `CREATOR` $\to$ `PROCESSOR 1` (2 канали, delay = 1.0)
* `PROCESSOR 1` розгалужується:
  * **$70\%$** $\to$ `PROCESSOR 2 (Inspection)`
  * **$30\%$** $\to$ `PROCESSOR 3 (Alt-Path)`
* `PROCESSOR 2` містить **зворотний зв'язок (Feedback Loop)**:
  * **$85\%$** $\to$ `DISPOSE` (вимогу прийнято)
  * **$15\%$** $\to$ **`PROCESSOR 1`** (повернення на доопрацювання у попередній блок)
* `PROCESSOR 3`: **$100\%$** $\to$ `DISPOSE`

### Результати верифікації переходів ($T = 1000$):
| Перехід потоку | Задана ймовірність | Фактична кількість переходів | Емпірична ймовірність | Похибка |
| :--- | :---: | :---: | :---: | :---: |
| **P1 $\to$ P2 (Розгалуження)** | **70.0%** | **382 / 531** | **71.9%** | $+1.9\%$ |
| **P1 $\to$ P3 (Розгалуження)** | **30.0%** | **149 / 531** | **28.1%** | $-1.9\%$ |
| **P2 $\to$ DISPOSE** | **85.0%** | **333 / 373** | **89.3%** | $+4.3\%$ |
| **P2 $\to$ P1 (Зворотний зв'язок)** | **15.0%** | **40 / 373** | **10.7%** | $-4.3\%$ |
| **P3 $\to$ DISPOSE** | **100.0%** | **149 / 149** | **100.0%** | $0.0\%$ |

### Підтвердження закону збереження вимог (Conservation Law):
* Створено джерелом `CREATOR` = **491** вимог.
* Повернуто за зворотним зв'язком з P2 до P1 = **40** вимог.
* Всього надійшло на вхід P1 = $491 + 40 =$ **531** вимог (повністю збігається з кількістю оброблених P1).
* **Глобальний баланс мережі:**
  $$\text{Створено (491)} = \text{DISPOSE (482)} + \text{Втрачено (8)} + \text{В чергах і каналах (1)} = \mathbf{491}$$
*Підсумок:* Рівняння балансу зійшлося з точністю до однієї вимоги, що математично доводить коректність роботи циклічних зворотних маршрутів.
